# Large-Scale Training Infrastructure（大規模な学習・推論インフラ）

**拡散モデルを実際に大規模で回すための工学**——複数 GPU への分散、メモリの節約、数値精度の削減——を扱うページである。本 wiki の他のページが「何を学習するか」（定式化・アーキテクチャ・損失）を扱うのに対し、ここは「**それを物理的にどう成立させるか**」を扱う。

なぜ独立したページが要るのか。**動画拡散（[[video-diffusion]]）に至って、インフラが設計上の制約から本質的な制約へ変わった**からである。Wan（[[summaries/2025-wan]]）の実測はその転換点を明快に示す：系列長 100 万トークンで**注意計算が学習時間の 95%**、14B モデルの活性化メモリは **8 TB**。画像生成では「モデルが単一 GPU に載らない」が主な難所だったが、動画では**1 サンプルの中間状態が載らない**。この差は量ではなく質の差であり、モデル設計の判断そのものに跳ね返る。

## まず何がボトルネックかを測る

Wan の負荷分析は、この種の議論の出発点として汎用性が高い。DiT の計算コストは

$$L(\alpha b s h^{2} + \beta b s^{2} h)$$

と書ける（$L$ は層数、$b$ はマイクロバッチサイズ、$s$ は系列長、$h$ は隠れ次元）。第 1 項は線形層で $s$ に**線形**、第 2 項は注意で $s$ の**二乗**。LLM では $s$ がせいぜい数千なので線形層が支配的だが、動画では $s$ が数十万から 100 万に達するので、**注意が全体を飲み込む**。

一方、GPU メモリは $\gamma L b s h$ で $s$ に**線形**にしかスケールしない（$\gamma$ は実装依存の係数。通常の LLM で 34 程度に対し、DiT は動画トークン・プロンプト・タイムステップを同時に入力するので 60 を超える）。

ここから、本ページで最も再利用価値の高い指針が導かれる：

> **計算は $s^2$、メモリは $s$ でスケールする。したがって系列が長くなるほど、「計算している間にメモリを別の場所へ退避する」時間的余裕が生まれる。**

この非対称性が、後述する「活性化オフロードを勾配チェックポインティングより優先する」という判断を直接根拠づける。

なお学習全体のうち **DiT が計算の 85% 以上**を占め、VAE とテキストエンコーダは凍結されて推論のみである。最適化の努力を DiT に集中させるべき、という配分の判断もここから出る。

## 分散のかけ方 — 何を軸に切るか

DiT ブロックの入力は $[b, s, h]$ という 3 つの軸を持つ。分散戦略は「**どの軸で切るか**」で分類できる。

| 軸 | 手法 | 何が分散されるか |
| --- | --- | --- |
| $b$（バッチ） | **DP**（Data Parallel） | サンプル。最も単純だが、1 サンプルが載らないと使えない |
| モデル重み | **FSDP**（Fully Sharded Data Parallel） | パラメータ・勾配・オプティマイザ状態 |
| $s$（系列長） | **CP**（Context Parallel）— Ulysses / Ring Attention | 活性化と注意計算 |
| $h$（隠れ次元） | **TP + SP**（Tensor + Sequence Parallel） | 重みを割って活性化の隠れ次元を分散 |

Wan は **$s$ 軸（CP）を主軸に選ぶ**。理由は $h$ 軸（TP+SP）より**通信オーバーヘッドが小さい**こと。動画では $s$ が突出して大きいので、切る軸として自然でもある。

### 2D Context Parallel — Ring と Ulysses を入れ子にする

系列長方向に注意を分散する方式には 2 つの代表があり、それぞれ弱点を持つ。

- **Ulysses**：全対全通信でアテンションヘッドを配り直す。通信量は少ないが、**全対全はマシンをまたぐと遅い**。
- **Ring Attention**：ブロックを環状に回しながら注意を計算する。通信を計算で隠せるが、**分割後の各ブロックが十分大きくないと隠しきれない**。

Wan の解は、この 2 つを**入れ子にする**ことである（USP と同様）——**外層に Ring Attention（マシン間）、内層に Ulysses（マシン内）**。外層を Ring にすることで遅いマシン間通信を計算で隠し、内層を Ulysses にすることでブロックサイズが小さくなりすぎる問題を避ける。

効果は明快で、系列長 256K・2 マシン・16 GPU の設定で、**通信オーバーヘッドが Ulysses 単独の 10% 超から 1% 未満へ**下がる。

128 GPU の具体的な構成例：CP=16（内訳 Ulysses=8, Ring=2）、FSDP=32、DP=4、グローバルバッチサイズはマイクロバッチの 8 倍。

### モジュールごとに戦略を切り替える

見落とされがちだが実務的に重要な最適化がある。VAE とテキストエンコーダは DP、DiT は DP＋CP を使う。ところが **CP は CP グループ内の全デバイスが同じデータを持つことを要求する**——素朴にやると、VAE とテキストエンコーダの段階でも同じデータを全デバイスが重複して処理してしまう。

Wan の解は「**CP グループ内のデバイスは最初は別々のデータを読み、CP に入る直前に順次ブロードキャストして揃える**」。これで VAE とエンコーダの実行時間が $1/CP$ に圧縮される。**同じ資源を使い回すパイプラインでは、段ごとに分散戦略を切り替える必要がある**という一般則の実例である。

## メモリ — 再計算か、退避か

活性化メモリを減らす手段は大きく 2 つある。

- **勾配チェックポインティング（GC）**：順伝播の活性化を捨てて、逆伝播時に**再計算**する。メモリは減るが計算が増える。
- **活性化オフロード**：活性化を **CPU メモリへ退避**し、必要になったら戻す。計算は増えないが PCIe 転送が要る。

一般に GC が定番だが、Wan は**オフロードを優先する**。根拠は冒頭の非対称性である——1 つの DiT 層の活性化をオフロードする PCIe 転送時間は、**わずか 1〜3 層分の計算時間で隠せる**。系列が長いほど計算時間が伸びるので、転送を完全に裏に回せる。つまり**長い系列ほどオフロードが有利**になる。

ただし CPU メモリも無限ではないので、実際には併用する——**GPU メモリと計算量の比が高い層から優先的に GC を掛ける**という配分をとる。

## 推論 — レイテンシを削る 3 つの掛け算

学習と推論で最適化の目標が変わる。学習はスループット（単位時間あたりの処理サンプル数）、推論は**レイテンシ**（1 本の動画が出るまでの時間）である。しかも推論は約 50 ステップの逐次処理なので、**1 ステップを速くする**か**ステップ数を減らす**しかない。

Wan は 3 つを掛け算する。

**(1) 分散**（1 ステップを並列化）。学習と同じ 2D Context Parallel ＋ FSDP。**ほぼ線形の高速化**が得られる。長い系列は分散の粒度を細かくできるので、動画は分散と相性が良い。

**(2) 推論キャッシュ**（1 ステップの中身を削る）。ステップ間の注意出力の類似性と CFG の類似性を突いて **1.62×**。詳細は [[inference-caching]] に分離した。

**(3) 量子化**（1 演算を安くする）。

- **FP8 GEMM**：DiT ブロックの全 GEMM（行列積）を FP8 化。重みはテンソル単位、活性化はトークン単位の量子化。BF16 の 2 倍のスループットで、DiT モジュールとして **1.13×**。
- **8-bit FlashAttention**：ここが最も込み入っている。FlashAttention3 のネイティブ FP8 実装は**動画生成で有意に品質が落ちる**（画像では問題にならなかった精度が、系列長の桁が違うと足りなくなる）。Wan の対処は 2 つ：
  - **混合 8 ビット**：$S = QK^T$ には **Int8**、$O = PV$ には **FP8** を使う（SageAttention の知見に基づく使い分け）。
  - **FP32 累算**：FP8 WGMMA は 14 ビットの累算器を使うため長い系列でオーバーフローする。ブロック内は FP8 WGMMA のまま、**ブロック間の累算だけ CUDA コアの Float32 レジスタで行う**（DeepSeek-V3 の FP8 GEMM に着想）。
  - 性能面では Float32 累算を `rescale_o` と融合し、レジスタ圧に合わせてブロックサイズを調整して、**H20 GPU で 95% の MFU**（理論ピークに対する実効利用率）を達成。**1.27×**。

3 つ合わせて実用域に入る。それでも Wan 14B は**最適化なしで単一ハイエンド GPU に 1 本 30 分**であり、著者らは推論コストを主要な未解決課題として明記している。

**クラスタの信頼性**についても短く触れられている。数千 GPU 規模の学習では**ノード故障が日常的に起きる**ので、起動時のハードウェア検査、故障ノードの隔離と修復、タスクの自動再起動と再開が前提設備になる。研究の議論には現れにくいが、大規模学習が成立する条件の一部である。

## 限界と注意点

- **本ページの記述はほぼ Wan 単独に依存する**。他の大規模モデルのレポートは同種の詳細を公開していないことが多く、一般論として確立した知見はまだ薄い。
- **数値がハードウェア依存**。「95% MFU」「10% → 1%」といった値は特定の GPU・ネットワーク構成での測定であり、そのまま移植できない。
- **学習コストの総量が報告されない**。GPU 時間・総コストが書かれておらず、「効率的」という主張の絶対的な水準が測れない。
- **量子化の品質影響が定量化されていない**。「minimal performance loss」と述べられるが、品質比較の数値が示されない。とくに 8-bit FlashAttention は「FA3 のネイティブ FP8 は動画で品質劣化する」と自ら述べているので、対処後にどこまで戻ったかは重要な情報のはずである。
- **アルゴリズムとインフラの境界が動く**。ここに挙げた工夫の一部（たとえば注意の分散のしかた）は、アーキテクチャ側で系列長を減らせば不要になる。[[image-tokenizer]] の圧縮率設計や、注意を時空間に分解する設計は、**インフラの問題をモデル設計で回避する**アプローチにあたる。どちらで解くかは設計判断である。

## 既存知識との接続

- [[video-diffusion]]：本ページが独立して必要になった理由そのもの。系列長 100 万・活性化 8 TB という数字が、動画拡散を分散システムの問題にしている。
- [[diffusion-model-architecture]]：アーキテクチャの選択がインフラの負荷を決める。full spatio-temporal attention を採れば二次コストを正面から払うことになり、時空間に分解すれば軽くなる。adaLN 共有によるパラメータ削減も、メモリ制約への一つの答えである。
- [[image-tokenizer]]：**圧縮率の設計はインフラの問題でもある**。$f8 \to f16$ にすればトークン数は 4 分の 1 になり、注意は 16 分の 1 になる。[[summaries/2026-qwen-image-vae-2]] が高圧縮を追求する動機の半分はここにある。
- [[inference-caching]]：推論側の 3 つの軸のうち「1 ステップの中身を削る」を担当する。学習不要で他と併用できる。
- [[diffusion-distillation]]：推論の「ステップ数を減らす」側の答え。本ページの手法とは直交し、掛け算で効く。Wan は蒸留（LCM）・キャッシュ・量子化を同時に使う。
