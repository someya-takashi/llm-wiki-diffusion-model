# Prompt Enhancement（プロンプト拡張 / プロンプト書き換え）

**Prompt Enhancement（プロンプト拡張）** とは、**ユーザーが入力した短く曖昧なプロンプトを、言語モデルが自動的に詳細で構造化された記述へ書き換えてから生成モデルへ渡す**仕組みである。2025 年以降の主要な text-to-image / text-to-video システムはほぼ例外なくこれを備えており、**モデルの一部として設計され、評価され、ときに学習される**ようになった。

本 wiki が最初にこれに出会ったのは Qwen-Image-2.0 の Prompt Enhancer（[[summaries/2026-qwen-image-2]]）だったが、その後 Wan・HiDream-O1-Image・Z-Image がそれぞれ異なる設計を出しており、**同じ問題への 4 通りの答えが並ぶ**状態になった。本ページはそれを対比の形で整理する。

## なぜ必要になったのか — 分布のずれ

問題は 1 行で言える。**学習時のキャプションと推論時のユーザープロンプトは、まったく違う分布から来ている**。

[[data-curation]] で見た通り、現代の T2I モデルは専用のキャプションモデルが生成した**密で詳細な記述**（数百語規模、主語・目的語・背景・照明・構図・様式まで含む）で学習される。ところが実際のユーザーは「猫」「夕日の海」のように短く不完全に書く。Wan の言い方では「ユーザーは典型的に、学習キャプションよりも著しく短い、いくつかの単純な語から成る簡潔なプロンプトを好む」。

このずれは生成品質を直接下げる。モデルは「詳しく書かれた文」を条件とする写像を学んでおり、短い文が来ると学習分布の外側に置かれる。

対処は 2 方向ある。

1. **学習側を寄せる**：短いキャプション・タグ・**模擬ユーザープロンプト**を学習データに混ぜる（[[data-curation]]）。Wan も Z-Image もこれをやっている。
2. **推論側を寄せる**：ユーザーのプロンプトを LLM が書き換えて学習分布に近づける。これが本ページの主題である。

実際にはこの 2 つは併用される。

## 第二の動機 — 小さいモデルの認知的ギャップを埋める

分布のずれとは別に、もう 1 つ強い動機が現れた。**モデルを小さくしたい**という要求である。

Z-Image（[[summaries/2025-z-image]]）はこれを最も明確に述べる。6B という規模ゆえ「世界知識・意図の理解・複雑な推論において限界を示す」が、「**詳細なプロンプトを写実的な画像へ翻訳できる強力なテキストデコーダとしては優秀**」である。ならば認知的な部分は外付けの VLM に任せ、拡散モデルは描画に専念すればよい——**役割分担によってパラメータ数を節約する**という設計判断になる。

具体例が分かりやすい。地理座標を与えられたとき、素朴なシステムは**座標の文字列をそのまま画像に描く**。プロンプトエンハンサに推論をさせると、座標から場所（西湖）を割り出して**その風景を生成する**。「登科后」という詩題を与えられれば、LLM の事前知識から歴史的細部（疾走する馬、赤い官服）と有名な対句を取り出し、それを視覚的手がかりへ翻訳する。**6B の拡散モデルにこの知識を持たせるのは高くつくが、既存の VLM は無料で持っている**。

## 4 つの設計 — 何を動かし、何を固定するか

同じ「LLM でプロンプトを書き換える」でも、実装は驚くほど分かれる。整理軸は 2 つ：**推論連鎖を挟むか**と、**どちらを学習するか**である。

| | 書き換えモデル | 推論連鎖 | 学習の向き |
| --- | --- | --- | --- |
| **Wan**（[[summaries/2025-wan]]） | Qwen2.5-Plus（凍結） | なし | どちらも学習しない（プロンプト設計のみ） |
| **Qwen-Image-2.0**（[[summaries/2026-qwen-image-2]]） | Prompt Enhancer | なし | **PE を下流の画像品質で RL 最適化** |
| **HiDream-O1-Image**（[[summaries/2026-hidream-o1-image]]） | Gemma ベースの Prompt Agent | **あり**（thinking） | **推論品質そのものを報酬化して RL** |
| **Z-Image**（[[summaries/2025-z-image]]） | 事前学習済み VLM（**凍結**） | **あり** | **拡散側を PE の出力に合わせて SFT** |

### Wan — プロンプト設計だけで済ませる

最も素朴で、最も手軽な形。Qwen2.5-Plus に 3 つの原則を指示するだけで、モデルは一切学習しない。

1. 元の意味を変えずに詳細を加える。
2. **自然な動きの属性を組み込む**（被写体のカテゴリに応じた適切な動作を足す）——動画生成固有の要件で、静止しがちな出力を防ぐ（[[video-diffusion]]）。
3. **学習キャプションと同じ構成にする**：様式 → 内容の概略 → 詳細な記述の順。

3 番目が本質で、「分布を寄せる」という目的を最も直接的に実装している。

### Qwen-Image-2.0 — 書き換えを RL で最適化する

一歩進んで、**PE の出力が下流でどれだけ良い画像を生むか**を報酬にして PE 自体を最適化する（[[reinforcement-learning-for-diffusion]]）。書き換えが「うまい日本語かどうか」ではなく「**良い画像を生むかどうか**」で評価されるようになる。前処理が生成パイプラインの最適化対象に入った最初の例である。

### HiDream-O1-Image — 推論過程そのものを報酬化する

さらに進んで、Gemma ベースのエージェントが**空間配置・被写体の属性・物理的な論理・文脈的関係について思考の連鎖（chain of thought）を明示的に生成してから**最終プロンプトを出す。そして GRPO の 4 つの報酬のうち 1 つが「**推論品質**」である。中間の推論過程の質そのものが最適化対象になっている。

### Z-Image — 逆向きに合わせる

最も対照的なのがここで、**VLM を固定したまま、拡散側を VLM に合わせる**。SFT の段階で**すべての入力プロンプトを PE に通し**、その出力を条件として Z-Image を微調整する。

利点は明快である。**LLM の追加学習コストがゼロ**になる。大きな VLM を RL で回すのは高くつくが、6B の拡散モデルを SFT するのは安い。「小さい方を大きい方に合わせる」という選択で、Z-Image の「効率」という主題と一貫している。

一方で代償もある。**PE が変わると拡散側を学習し直す必要がある**——両者が固く結合するので、後から書き換えモデルを差し替えにくい。Qwen 系の「PE を動かす」設計とは、更新可能性の面で正反対の性質を持つ。

## 推論連鎖は何を足しているのか

Qwen-Image-2.0 と Wan には推論連鎖がなく、HiDream-O1-Image と Z-Image にはある。何が違うのか。

推論なしの書き換えは基本的に**装飾**である——短い記述を長く、曖昧な表現を具体的にする。推論ありは**演繹**を行う。Z-Image の構造化された推論連鎖は「中核となる主体の分析 → 問題解決／世界知識の注入 → 美的な強化 → 包括的な記述」という段階を踏み、途中で**プロンプトに書かれていない事実を導出する**。

分かりやすい例が Z-Image の 2 つの図である。

- **座標 → 場所**：推論なしなら座標の文字列を画像に描く。推論ありなら西湖だと割り出して風景を描く。
- **「プーアル茶を淹れる」の手順図**：推論なしなら一般的なリストが出る。推論ありなら各手順の具体的な図解を計画して生成する。

HiDream-O1-Image が「鶴亀算のような論理パズルを解いてから描く」ことを示すのも同じ性質である。**プロンプト拡張が、書き換えから推論へ移りつつある**——というのが 2026 年時点の流れになる。

## PE ありなしを分けて測る（2026）

上の「限界」で最初に挙げる問題——**評価が PE 込みか否かが曖昧**——に、**ERNIE-Image**（[[summaries/2026-ernie-image]]）は正面から答えている。全ベンチマークで **w/ PE と w/o PE を並記**するのである。しかも結果が一様でない点が示唆に富む。

| ベンチマーク／次元 | PE なし | PE あり | 向き |
| --- | --- | --- | --- |
| GenEval 総合 | **0.89** | 0.87 | **PE で下がる** |
| OneIG-EN の Alignment | **0.891** | 0.868 | **下がる** |
| OneIG-EN の Reasoning | 0.295 | **0.357** | 大きく上がる |
| OneIG-EN の Diversity | 0.169 | **0.241** | 上がる |
| OneIG-EN 総合 | 0.554 | **0.575** | 上がる |
| LongText-Bench 総合 | 0.964 | **0.973** | 上がる |

読み取れる構図は明快である。**PE は推論と世界知識を要する次元を大きく押し上げる一方、素朴な整合や物体属性の遵守ではむしろ邪魔になる**。GenEval のような「プロンプトに書かれた通りに物を置く」タスクでは、プロンプトを膨らませることが**元の指定を薄める**方向に働く——上の限界で挙げた「ユーザーの意図の書き換え」が、数字で見える形になった数少ない例である。

一方で **Diversity が上がる**（0.169 → 0.241）のは興味深い。PE は「指定されなかった要素を勝手に決める」ので多様性を下げると予想されたが、短いプロンプトから毎回違う展開を作ることで、逆に出力の幅が広がる場合がある。**PE の多様性への効果は一方向ではない**。

### PE の規模はどこまで効くか

ERNIE-Image は **3B の PE** と**より大きな LM の PE** も比較する。3B でも構造化された生成（ホワイトボードの数式、RPG の HUD、Web ページのレイアウト）に実践的な利得が出る。より大きな LM は「より密な世界知識・より良い推論・より精密な構造的制約」を持つプロンプトを生成し、**自明でない推論を要するタスクでさらに伸びる**——ホワイトボードの例では数学的導出の正確さと完全性に差が出る。

つまり PE には**規模のスケーリングが効く**。生成モデル本体を大きくする代わりに PE を大きくするという選択肢があり、これは Z-Image と ERNIE-Image に共通する「小さい生成器＋外付けの認知」という設計の延長線上にある。

## 5 つ目の設計 — 書き換えをモデルの中に入れる（2025）

上の表に並べた 4 通りは、**どれも外付けのモジュール**だった。書き換えモデルを凍結するか学習するかは分かれても、拡散モデルとは別のネットワークが前段に立つ点は共通していた。

**HunyuanImage 3.0**（[[summaries/2025-hunyuanimage-3]]）は 5 つ目の点を示す——**前段を置かず、モデル自身が「思考」の局面を通る**。土台が大規模言語モデルなので（[[unified-multimodal-generation]]）、推論はもともとできる。あとはそれを画像生成の前に実行させればよい。

| | 書き換えモデル | 推論連鎖 | 学習の向き |
| --- | --- | --- | --- |
| **HunyuanImage 3.0** | **なし（モデル自身）** | **あり（ネイティブ CoT）** | **推論トークンも次トークン予測で学習** |

引き出し方は小規模な推論データでの微調整である。**T2T**（テキスト→テキスト：プロンプトから精緻化された記述への段階的推論）と **T2TI**（テキスト→テキスト→画像：抽象的な概念から視覚的な顕現までのワークフロー全体）。実装上の要点として、**推論部分のトークンもまた自己回帰的な次トークン予測でモデル化される**——テキストは AR、画像は拡散という HunyuanImage 3.0 のハイブリッド構造が、ここで直接効いている。

内部化には明快な利点がある。上の「限界」で挙げた **実効的なパラメータ数が不透明**という問題が消える——推論も生成も同じモデルなので、「6B」と言いながら別の VLM が裏で動く、という状況が起きない。ベンチマークの数値が何を測っているかも曖昧にならない。

代わりに 2 つの代償を負う。**(1) 分離できない**。Z-Image の PE は差し替えられる（もっとも拡散側を再学習する必要はある）が、内部化された CoT はモデルの一部なので独立に更新できない。**(2) 大きな LLM が要る**。外付けなら小さい生成器に大きな VLM を足せるが、内部化するには生成器自身が推論できるだけの容量を持たねばならない——HunyuanImage 3.0 が 80B（活性 13B）である理由の一端はここにある。

**外付けと内部化のどちらが良いかは決着していない**。Z-Image と ERNIE-Image は「小さい生成器＋外付けの認知」で高い効率を達成し、HunyuanImage 3.0 は「大きな統一モデル」で同じ問題を内側から解く。しかも **HunyuanImage 3.0 は CoT ありなしの比較数値を示さない**ので、内部化の利得すら定量化されていない（ERNIE-Image が PE ありなしを分離報告したのと比べると後退している）。

## 6 つ目の設計 — 書き換えず、埋め込みの質を変える（2024）

ここまでの 5 通りは、程度の差はあれ**プロンプトのテキストを書き換える**ものだった。だが「LLM に賢く前処理させる」目的は、テキストを経由しなくても達成できる。

**Sana**（[[summaries/2024-sana]]）の **Complex Human Instruction（CHI, 複雑な人間の指示）** がその例である。Sana はテキストエンコーダに T5 ではなく **Gemma-2-2B**（デコーダのみの小型 LLM）を使うが、素朴に使うと問題が起きる——LLM は指示に従って**会話する**よう訓練されているので、プロンプトをそのまま入れると内部表現が「これに返答しよう」という方向に寄り、**プロンプトそのものの理解に焦点が当たらない**。

そこで CHI——「あなたは画像生成のプロンプトを解釈する助手である」といった文脈内学習用の指示文——をユーザープロンプトの前に置く。**出力テキストを取り出して使うのではなく、CHI を前置した状態でのテキスト埋め込みをそのまま拡散モデルの条件にする**。GenEval で +2.0〜2.2 ポイント（52K ステップで 45.5 → 47.7、140K 相当で 52.8 → 54.8）。

| | 書き換えモデル | 何を変える | 追加レイテンシ |
| --- | --- | --- | --- |
| **Sana（CHI）** | **なし（テキストエンコーダ自身）** | **埋め込みの質**（テキストは書き換えない） | **ほぼゼロ**（前置トークンの分だけ） |

**この設計の利点は、上の「限界」で挙げた問題の多くが構造的に発生しないこと**である。ユーザーの意図が別の言葉に書き換えられることがないので意図の書き換えは起きず、中間の書き換えテキストがないので「PE 込みで測ったのか」という評価の曖昧さも生じない。実効パラメータ数の不透明さもない——Gemma-2-2B はもともと必要なテキストエンコーダである。レイテンシも、書き換えモデルを別途走らせる方式と比べれば無視できる。

代償は**できることの上限が低い**ことである。CHI は埋め込みの向きを整えるだけで、Z-Image の PE のように「座標を解釈する」「世界知識で欠落を補う」といった能動的な推論はできない。書き換え型と競合するものではなく、**より下の層で効く別の道具**と見るのが正しい。実際、CHI を入れた上で外付けの PE を併用することは何も妨げない。

なお Sana はこの設計から予期しない副産物も得ている——**学習は英語プロンプトのみなのに、中国語や絵文字を入力しても意図どおりの画像が出る**。Gemma-2 の事前学習が持つ多言語能力が、テキストエンコーダを LLM にしたことでそのまま転移した。T5 ベースでは得られなかった性質である。

**CHI の弱点は測定が間接的なこと**。原典は「LLM の出力とテキスト埋め込みの品質の間に強い正の相関が存在すると考える」と述べるが、これは仮説であって検証されていない。CHI 文自体の設計もアドホックで、なぜその文面が良いのかの分析はない。

## 実装から読める「書き換えの中身」（FLUX.2）

本ページはこれまで各社の**設計**（何を凍結し何を学習するか）を比較してきたが、**書き換えの指示文そのもの**を見られる例は少なかった。FLUX.2 のリファレンス実装（[[summaries/2025-flux2]]）は `system_messages.py` にそれを平文で持っている。

**T2I 用**の指示は 3 項目で、うち 1 つが本 wiki の別の論点に直結する。

> **Text in Images**: Put ALL text in quotation marks, matching the prompt's language. Always provide explicit quoted text for objects that would contain text in reality (signs, labels, screens, etc.) — **without it, the model generates gibberish.**

**「引用符で囲まないと文字が意味のない記号列になる」**——これは [[concepts/visual-text-rendering]] の問題を、モデル側ではなく**プロンプト側の規約**で回避している。Qwen-Image が VAE デコーダの微調整やデータ合成で解いた問題（[[summaries/2025-qwen-image]]）に対し、FLUX.2 は「書き換え器に必ず引用符を付けさせる」という運用で当てている。**PE がモデルの弱点を隠す層としても働いている**例である。

**I2I（編集）用**の指示はさらに具体的で、[[concepts/instruction-based-image-editing]] の要請がそのまま規則になっている。

- **Specify what changes AND what stays the same**（顔・照明・構図）
- **Turn negatives into positives**（"don't change X" → "keep X"）
- Make abstractions concrete（"futuristic" → "glowing cyan neon, metallic panels"）

「変えるべき所だけ変える」という編集の中心課題を、**モデルに推論させるのではなく指示文で明示化する**方針である。

**構成上の注意点が 1 つある。** 書き換えには API 経由（OpenRouter）とローカルの 2 経路があるが、**ローカル書き換えは dev のテキストエンコーダ（Mistral-Small-3.2-24B）でしか動かない**。klein の `Qwen3Embedder` は `upsample_prompt` に `NotImplementedError` を投げる。つまり **klein は PE をモデル内に持たない**——本ページの分類でいえば「外付け必須」であり、Z-Image のように拡散側を PE 出力分布へ合わせる（PE-aware SFT）こともしていない。**軽量化のために PE を切り離した**とも読めるが、その分だけ推論時の分布のずれは利用者側の責任になる。

## 実装から読める「符号化の作法」（Z-Image, 2026-08-26 追記）

本ページは前節で FLUX.2 の system message（書き換えの中身）を読んだ。Z-Image のリファレンス実装（[[summaries/2025-z-image]]）を読むと、**書き換えの前段——LLM をどう呼び出して埋め込みを取るか——にも設計変数がある**ことが分かる。

```python
# src/zimage/pipeline.py L110–116
messages = [{"role": "user", "content": p}]
formatted_prompt = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=True, enable_thinking=True,
)
```

**プロンプトは Qwen の chat template で整形され、`add_generation_prompt=True` と `enable_thinking=True` まで付く。** つまりテキストエンコーダは「これから応答を生成する直前の対話状態」として符号化される——にもかかわらず、**生成は一切行われない**。取り出すのは隠れ状態だけである。

なぜこうするのか。報告書には記述がないが、合理的な読みは 2 つある。第一に、**Qwen3-4B は chat 形式で事後学習されている**ので、生の平文よりも chat template を通したほうが「指示を理解しようとしている」状態の表現が得られる。第二に、`enable_thinking=True` は思考プロンプトを挿入するので、**モデルが「これから推論する」構えの表現を作る**。本ページが「推論連鎖は何を足しているのか」で論じた効果を、**生成コストを払わずに埋め込み側だけで拾おうとしている**、と解釈できる。効果の有無は測定されていない（コードからは分からない）。

**どの層を取るかも設計変数である。**

```python
# 同 L134
prompt_embeds = text_encoder(...).hidden_states[-2]
```

**最終層ではなく 1 つ手前**を取る。[[summaries/2025-flux2]] が中間 3 層（Mistral なら 10/20/30、Qwen3 なら 9/18/27）を連結するのと同じ問題意識——**最終層は次トークン予測に特化しすぎており、条件付けに使う意味表現としては手前のほうが良い**——に、より軽い答えを出したことになる。CLIP の penultimate layer を使う Stable Diffusion 以来の作法とも連続している。

本ページの整理に **7 つ目の設計**を加えるなら、こうなる——**書き換えもせず、埋め込みの内容も変えず、「LLM をどのモードで呼ぶか」だけを変える**。CHI（[[summaries/2024-sana]]）が指示文を前置して埋め込みの質を変えたのに対し、こちらは**呼び出しの作法（chat template・thinking フラグ・取り出す層）**というさらに下の層での介入である。

なお Z-Image の立場そのもの——**PE を凍結し拡散側を PE の出力分布に合わせる**——は変わらない。上記は PE の下流にある符号化器側の話であり、[[questions/z-image-architecture-and-lora-placement]] が指摘した「学習キャプションを PE の出力分布に合わせよ」という実務上の注意もそのまま有効である。

## 限界と注意点

- **評価が PE 込みか否かが曖昧**。これが最も深刻な問題である。ベンチマークのスコアが PE ありで測られたのか無しなのか、明示しないレポートが多い。Z-Image は付録で「PE を無効にすれば図 1–3 を再現できる」と述べるが、本文のベンチマーク数値がどちらかは書かれていない。**6B の性能の何割が VLM 由来なのかを切り分けられない**。
- **実効的なパラメータ数が不透明**。Z-Image は「6B」を看板にするが、推論時には別途 VLM が動く。**システム全体の規模とレイテンシは 6B ではない**。他モデルとの「パラメータ数比較」は、この点で公平でない可能性がある。
- **ユーザーの意図の書き換え**。エンハンサは「詳細を加える」と称して、ユーザーが指定しなかった要素（構図・照明・様式）を勝手に決める。ユーザーが意図的に曖昧にしていた部分まで固定してしまうので、**多様性が下がる**方向に働く。Z-Image の OneIG Diversity スコアが低い（0.194、Turbo は 0.139）ことに、PE がどれだけ寄与しているかは測られていない。
- **失敗が見えにくい**。エンハンサが誤って推論すると（例：座標を間違った場所と解釈する）、ユーザーには「なぜこの画像が出たのか」が分からない。中間表現が不可視な分、デバッグしづらい。
- **アブレーションが薄い**。「PE ありの方が良い」という定性的な図は示されるが、ベンチマーク上での PE の寄与を定量化した比較はどのレポートにも乏しい。
- **推論連鎖のコスト**。thinking を挟めば当然レイテンシが伸びる。Z-Image が「サブ秒の推論」を謳う一方、それが PE を含む時間なのかは不明である。

## 既存知識との接続

- [[text-to-image-generation]]：プロンプト追従性能の議論は、本来「モデルがどれだけ指示を理解するか」だったが、PE の登場で「**システムがどれだけ理解するか**」に変わった。ベンチマークの解釈にこの区別が必要になる。
- [[data-curation]]：問題の根は学習キャプションと実ユーザー入力の分布のずれにある。学習側で模擬ユーザープロンプトを混ぜるのと、推論側で書き換えるのは、**同じ問題への両側からの対処**であり、実際には併用される。
- [[reinforcement-learning-for-diffusion]]：Qwen-Image-2.0 と HiDream-O1-Image は PE を RL の最適化対象に含める。**前処理・生成本体・事後学習が 1 つの最適化ループに入る**という流れの一部。
- [[instruction-based-image-editing]]：編集でも PE は効く。曖昧な指示の解釈（「もっと良くして」）と、世界知識を要する編集（材料から料理を推論する）で、Z-Image と HiDream-O1 が同様の効果を報告している。
- [[video-diffusion]]：Wan の書き換え原則に「自然な動きの属性を組み込む」が入るのは動画固有。静止しがちな出力への対処である。
- [[diffusion-model-architecture]]：テキストエンコーダを decoder-only LLM に替える潮流（Sana → Qwen-Image → HunyuanImage 3.0 → ERNIE-Image）が、CHI のような「埋め込みの質を整える」層の PE を可能にした。エンコーダの選択が PE の設計余地を決めている。
