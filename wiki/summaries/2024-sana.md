# Sana: 線形 Diffusion Transformer による効率的な高解像度画像合成

> 原典: [[translations/2024-sana]] ・ `raw/papers/Sana_ Efficient High-Resolution Image Synthesis with Linear Diffusion Transformers.md`
> 著者・年・会議: Enze Xie, Junsong Chen, Song Han ら（NVIDIA / MIT / 清華大学）, 2024, arXiv:2410.10629（ICLR 2025）

## 一言まとめ

**トークン数を減らす（32 倍圧縮オートエンコーダ）・トークンあたりのコストを下げる（線形注意）・ステップ数を減らす（Flow-DPM-Solver）** という 3 方向の削減を同時にかけることで、0.6B という小さな拡散モデルで FLUX-12B（120 億パラメータ）に匹敵する画質を出し、4096×4096 の生成で**実測 100 倍以上のスループット**を達成した text-to-image モデル。16GB のノート PC 用 GPU 上で 1024×1024 を 1 秒未満で生成できる。

## 背景と問題意識

2024 年の text-to-image は「大きくすれば強くなる」路線を突き進んでいた。PixArt-α の 0.6B から SD3 の 8B、FLUX の 12B、Playground v3 の 24B へとパラメータが膨張し、学習も推論もクラウドの高価な GPU なしには回らなくなっていた。Sana はこの潮流に対して逆方向の問いを立てる——**「クラウドでもエッジでも高速に動く、高品質・高解像度の生成器は作れるか？」**

拡散 Transformer（DiT, Diffusion Transformer。U-Net の代わりに Transformer で拡散のノイズ予測を行うアーキテクチャ。[[diffusion-model-architecture]] 参照）の計算コストは、大まかに次の 3 因子の積で決まる。

1. **潜在トークン数 N**：[[latent-diffusion]] では画像をオートエンコーダで潜在空間に落としてから拡散する。圧縮率 F と patch size P で N = (H/F/P)×(W/F/P)。
2. **トークンあたりのコスト**：通常の自己注意は N に対して O(N²) なので、高解像度で N が増えると注意が支配的になる。
3. **サンプリングステップ数 T**：拡散は反復的にノイズを除去する（[[diffusion-sampling]]）。

既存研究はこのうち 1 つずつしか攻めていなかった。Sana の主張は「3 つ全部を同時に削っても品質は保てる、ただし各所で補償の工夫が要る」というものである。

### (1) 深圧縮オートエンコーダ AE-F32C32P1 — トークン数を 1/4 に

Stable Diffusion 系の VAE（Variational Autoencoder, 変分オートエンコーダ）は空間解像度を 8 倍圧縮する（F8）のが定番で、そのぶん DiT 側で patch size 2（P2）にしてトークン数をさらに 1/4 にしていた。Sana は**圧縮の担当を AE 側に寄せる**。F32C32P1、すなわち空間を 32 倍圧縮し、潜在チャネルを 32 に増やし、DiT の patchify は 1×1（＝何もしない）にする。

同じ最終トークン数になる組み合わせ（F8C16P4 / F16C32P2 / F32C32P1）を 1024px で比べたアブレーション（原典 表1）が本質的で、**F32C32P1 だけが収束も速く FID も最良**だった。理由は「圧縮を patchify（学習される線形射影 1 枚）に任せるより、深いオートエンコーダに任せた方が情報の圧縮が上手い」という単純なもので、[[image-tokenizer]] の設計指針として重要な知見である。ただしチャネル数 C は大きければ良いわけではなく、C=32 が最良で C=64 では再構成は改善しても生成の FID は悪化した（潜在空間が複雑すぎて拡散モデルが学習しにくくなる）。

### (2) 線形 DiT — 注意を O(N²) から O(N) へ

通常の softmax 注意は $\text{Softmax}(QK^\top)V$ を計算するため N×N の行列を作る。Sana は softmax を **ReLU カーネル**に置き換え、行列積の結合則を使って計算順序を入れ替える。

$$O_i = \frac{\sum_j \text{ReLU}(Q_i)\text{ReLU}(K_j)^\top V_j}{\sum_j \text{ReLU}(Q_i)\text{ReLU}(K_j)^\top}$$

分子の $\sum_j \text{ReLU}(K_j)^\top V_j$ は **i に依存しない d×d 行列**なので、一度だけ計算して全クエリで使い回せる。これで計算量は O(N²d) → O(Nd²) になり、トークン数 N に対して線形になる（詳細は [[efficient-attention]]）。

ただし線形注意に置き換えるだけでは FID 18.7 → 21.5、CLIP Score 24.9 → 23.3 と明確に劣化する（原典 表12）。Sana はこれを **Mix-FFN**——FFN の中に 3×3 depthwise convolution を挟み、GLU（Gated Linear Unit）と組み合わせたもの——で補償し、FID 18.9 / CLIP 24.8 とほぼ元に戻す。畳み込みが局所的な位置情報を暗黙に与えるため、**Positional Embedding を完全に取り除いても（NoPE, No Positional Encoding）性能が落ちない**という副産物も得られた（[[position-embedding]]）。なお 2K/4K への微調整時には PE を再導入している点は注意が必要で、NoPE が万能なわけではない。

### (3) デコーダのみのテキストエンコーダ ＋ 複雑な人間の指示（CHI）

T5-XXL（4.7B、エンコーダ-デコーダ型）を **Gemma-2-2B**（デコーダのみの小型 LLM）に置き換える。トークン長 300 での推論レイテンシは 1.6 秒 → 0.3 秒（原典 表13）。ただし素朴に置き換えると学習が不安定になるため、テキスト埋め込みに RMSNorm を適用し、**学習可能なスケール係数を 0.01 で初期化**して分散を揃える。

さらに、LLM は本来「指示に従って会話する」よう訓練されているので、プロンプトをそのまま食わせると出力が会話的になってしまう。Sana は **Complex Human Instruction（CHI, 複雑な人間の指示）** ——「あなたは画像生成のプロンプトを解釈する助手である」といった文脈内学習用の指示文——を前置し、Gemma-2 の内部表現を「プロンプトの詳細を理解し強化する」方向に誘導する（[[prompt-enhancement]] のうち、生成テキストではなく**埋め込みの質**を改善する側の手法）。GenEval で +2.0〜2.2 ポイントの改善が得られた。

面白い副作用として、**学習は英語プロンプトのみで行ったのに、中国語や絵文字を入力しても意図どおりの画像が生成される**（原典 図14）。これは Gemma-2 の事前学習が持つ多言語能力がそのまま転移したもので、T5 ベースでは得られなかった性質である。

### (4) Flow-DPM-Solver — 20 ステップで収束させる

[[flow-matching]]（rectified flow）は速度 $v$ を予測するが、Sana は **DPM-Solver++ を flow ベースに移植**する。鍵は「t≈T（ほぼ純ノイズ）の領域で何を予測させるか」で、付録 B に Tweedie の公式を使った分析がある。

t≈T では $x_0$ と $x_t$ がほぼ独立になるため、ノイズ予測モデルの最適解は $x_t$ の**線形関数に退化**する。この線形項を積分する際の離散化誤差が大きく、しかも t=T での誤差は以降の全ステップに伝播する。一方**データ予測モデルは t≈T でほぼ定数** $\mathbb{E}[x_0]$ に近づき、定数の積分の方が誤差が小さい。そこで Sana は速度予測モデルの出力を $x_\theta = x_t - \sigma_t v_\theta$ でデータ予測に変換してからソルバーに渡す。結果、Flow-Euler が 30–50 ステップ必要なところを **10–20 ステップ**で収束させる（[[diffusion-sampling]] / [[noise-schedule]]）。

### (5) データ側とシステム側

- **マルチキャプション ＋ CLIP-Score サンプラ**：1 枚の画像に対し複数の VLM（Vision Language Model）で 4 つのキャプションを生成し、学習時は CLIP スコアを温度付き確率で重み付けしてサンプリングする。ランダム選択（CLIP 27.13）より一貫して良い（27.26）。[[data-curation]] の観点では「多様性を確保しつつ品質の高いものを優先的に引く」設計。
- **W8A8 量子化 ＋ Triton カーネル融合**：ReLU 活性化を QKV 射影の末尾に、精度変換やパディングを行列積の先頭に融合する。学習 1.37×・推論 1.65× の高速化（[[large-scale-training-infrastructure]]）。
- **CAME-8bit ＋ Flow-DPM-Solver ＋ 量子化**で、16GB のラップトップ GPU 上に展開可能。

## 実験結果と知見

主要な結果（原典 表6/表7、表14）：

| モデル | パラメータ | 1024px スループット | 4096px 高速化倍率 | GenEval |
| --- | --- | --- | --- | --- |
| FLUX-dev | 12.0B | 0.04 /s（基準） | 1.0× | 0.67 |
| FLUX-schnell | 12.0B | 0.50 /s | 13.0× | 0.71 |
| SD3-medium | 2.0B | 0.28 /s | 4.0× | 0.62 |
| PixArt-Σ | 0.6B | 0.40 /s | 5.0× | 0.54 |
| **Sana-0.6B** | 0.6B | **1.72 /s** | **104.0×** | 0.64 |
| **Sana-1.6B** | 1.6B | 1.01 /s | 66.0× | 0.66 |

読み取るべき点：

- **高速化の倍率は解像度が上がるほど伸びる**（512px で 44.5× → 4096px で 104×）。これは線形注意の O(N) と深圧縮 AE によるトークン削減が、N が大きいほど効くという理論どおりの挙動である。逆に低解像度では優位性は小さい。
- **Sana-0.6B は FLUX-dev と GenEval でほぼ並ぶ（0.64 vs 0.67）が、FLUX-schnell（0.71）には届かない**。「12B と同等」は総合スコアの話であって全指標で勝っているわけではない。
- MJHQ-30K の FID では Sana-1.6B が 5.76 と、比較対象中で最良に近い値を出す。
- ヒトによる評価（原典 図9）では 1024px で PixArt-Σ・SD3 に対して優勢、FLUX-dev に対してはほぼ互角。

アブレーションで特に価値があるもの：

- **オートエンコーダの設計（表1）**：F32C32P1 > F16C32P2 > F8C16P4。「圧縮は patchify でなく AE にやらせろ」。
- **ブロック設計（表12）**：線形注意単体では劣化するが Mix-FFN で回復する。カーネル融合は品質に影響しない（当然だが実測で確認されている）。
- **スケジュール（表3）**：Flow Matching は DDPM に対し FID 19.5 → 16.9、CLIP 24.6 → 25.7。[[flow-matching]] の優位を 120K ステップという同一条件で示した数少ない直接比較のひとつ。

## 限界・批判的視点

- **NoPE は 1K までの話**。付録 B に「2K モデルの微調整では性能改善のため PE を再導入する」と明記されている。本文が強調する「位置符号化なしで動く」という主張は解像度に条件づけられており、要約だけ読むと誤解しやすい。高解像度の外挿では結局 PE の補間戦略（PixArt-Σ 方式）が必要になっている。
- **深圧縮 AE の再構成品質の上限**。F32 の圧縮は細かいテクスチャや小さな文字の再現に不利なはずだが、原典は図12 の定性比較にとどまり、rFID などの定量的な再構成品質の比較を主要部分に出していない。[[visual-text-rendering]]（画像内の文字レンダリング）の評価が事実上ないのは、この時期のモデルとしても弱点で、後続の Qwen-Image 系が重視した軸がまるごと抜けている。
- **CHI の効果の測定が間接的**。CHI ありなしで GenEval が +2.0 改善するのは示されるが、「LLM の出力とテキスト埋め込みの品質に強い正の相関があると考える」という記述は仮説であり検証されていない。CHI プロンプトの設計自体もアドホックである。
- **線形注意の一般性**。ReLU 線形注意は「品質を犠牲にせず」と述べられるが、実際には表12 で明確に劣化しており、Mix-FFN という別の帰納バイアス（畳み込み）で埋め合わせている。つまり「注意を安くしても畳み込みで補える程度のタスクだった」とも読め、より長い文脈や複雑な合成的推論を要する場面で同じ補償が効くかは未検証である。
- **比較の非対称性**。Sana は 4096px を生成できると謳うが、その 4K は 2K からの微調整によるもので、FLUX 等が同解像度でネイティブに学習されているわけでもない。表14 の 4096px 比較は各モデルにとって想定外の解像度での測定を含む。

## 位置づけ

Sana は[[latent-diffusion]]の枠組みの中で、**効率を「モデルを小さくする」ではなく「表現の粒度を粗くする」方向で稼いだ**点に独自性がある。同じ効率化でも [[diffusion-distillation]]（DMD・LCM などでステップ数を削る）や [[inference-caching]]（計算結果の再利用）とは直交する軸であり、実際 Sana は Flow-DPM-Solver でステップも削っているので、両方を掛け合わせている。

その後の系譜を見ると、深圧縮オートエンコーダの発想は Z-Image の f16/32ch や Qwen-Image-VAE 2.0 の高圧縮化に受け継がれ、「デコーダのみの LLM をテキストエンコーダにする」路線は Qwen-Image・HunyuanImage 3.0・ERNIE-Image が全面採用するに至った。一方、**線形注意は主流にならなかった**——後続の大規模モデルはむしろ FlashAttention と FP8 でフル注意を高速化する道を選んでいる（[[large-scale-training-infrastructure]]）。Sana の遺産は「注意を安くする」部分ではなく「潜在トークンを減らす」部分と「テキストエンコーダを LLM にする」部分にあると評価するのが公平だろう。

## 用語と略称

- **AE / VAE** = (Variational) Autoencoder, （変分）オートエンコーダ。画像を低次元の潜在表現に符号化・復号する。
- **DiT** = Diffusion Transformer, U-Net の代わりに Transformer を用いる拡散モデル。
- **F32C32P1** = 空間圧縮率 32、潜在チャネル 32、DiT の patch size 1 という Sana の設定。
- **NoPE** = No Positional Encoding, 位置符号化を用いないこと。
- **PE** = Positional Encoding / Embedding, 位置符号化。
- **CHI** = Complex Human Instruction, LLM テキストエンコーダに前置する文脈内学習用の指示文。
- **GLU** = Gated Linear Unit, 出力の一部をゲートとして掛け合わせる FFN の構成。
- **Mix-FFN** = 3×3 depthwise convolution を組み込んだ FFN。
- **FID** = Fréchet Inception Distance, 生成画像の品質を測る指標（低いほど良い）。
- **CLIP Score** = 画像とテキストの整合度を CLIP の埋め込み類似度で測る指標（高いほど良い）。
- **GenEval / DPG-Bench** = 物体数・色・位置などの指示追従性を測る text-to-image ベンチマーク。
- **W8A8** = 重み 8bit・活性化 8bit の量子化。
- **VLM** = Vision Language Model, 画像を理解して言語を出力するモデル。ここではキャプション自動生成に使う。
- **Tweedie の公式** = ノイズを加えた観測から元データの事後平均を、対数密度の勾配（スコア）で表す関係式。
